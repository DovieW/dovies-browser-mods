# Selected Browser Mods workflows

Status: scope and architecture plan, 2026-11-16. These are modules of **one extension**, with a common popup, options, shortcut registry and settings system. No new feature below is implemented by this document. The existing [migration backlog](migration.md) remains; these additions do not silently replace it.

The reference projects describe useful behavior. Implement our own selected workflows; do not import their source, assets, branding or entire feature sets. Use maintained libraries for difficult archive/media/PDF primitives when justified, with the existing dependency review.

## Confirmed product choices

- **Redact** is the selected renderer for the redesigned extension-page UI. Keep the measured performance and compatibility gates in the [UI decision](decisions/2026-11-16-ui-runtime.md). The first Redact workspace shell is implemented; native maintenance screens remain linked from options. See [UI interaction](ui-interaction.md).
- **Full-page screenshots:** one keyboard shortcut starts capture and automatically copies the complete image to the clipboard, without a manual preview/save step. PDF export is required for larger pages. "Instant" means minimal interaction and fast completion, not a promise of zero capture time on arbitrarily long pages.
- **Extension management:** search, individual toggles, saved profiles and bulk toggling are required.
- **Extension package export:** save `extension-name-v1.2.3.zip`, using the actual package version and placing the extension files directly at ZIP root, with `manifest.json` at the root. A source browser/editor is not needed.
- **Video saving:** deliver one usable video file with the expected picture and sound. MP4 is preferred where suitable, but another playable container is acceptable. A playlist, URL list, separate audio/video tracks or a directory of fragments is not the requested result.
- **Mono audio:** per-tab toggle, reversible to normal audio.
- **Selection highlighting and refresh:** keep their basic workflows simple. Proposed matching options and refresh restart/interval behavior below are implementation defaults to verify against use, not extra requested feature sets.

## Feature design and acceptance

### Full image clipboard and large-page PDF

Keep the existing visible-page screenshot command's behavior and ID. Add a distinct full-page copy action in the typed catalog, reusing active-tab/navigation safeguards and clipboard infrastructure. The new workflow must capture the full intended page, then copy the complete bitmap automatically. PDF is a real first-version output for larger pages, not an indefinite follow-up. Keep PDF and composition code out of ordinary popup startup.

Prototype capture paths before selecting one: scrolling/stitching through `captureVisibleTab`, versus an explicitly activated debugger/CDP capture if its performance gain warrants the privilege and interaction cost. The documented visible-tab API allows only two captures per second, so do not promise an arbitrarily long scroll-and-stitch capture is instantaneous. CDP exposes screenshot/PDF operations, but their behavior through the extension debugger API must be verified on supported Chrome versions before adoption; it is not a guaranteed shortcut to every page/output.

Bound total pixels, temporary blobs and composition memory; use tiled/paginated PDF output instead of allocating an unlimited canvas. Preserve the image's useful resolution. Test normal and extremely long pages, zoom/device scale, fixed/sticky elements, nested scrolling, lazy content, navigation/tab switching, cancellation and clipboard failure. Restore any changed page state on completion/error. Confirm that a paste receives the whole bitmap and that PDF pages are complete and legible. Do not silently replace a failed full capture with a viewport image.

Sources: [tabs/capture limits](https://developer.chrome.com/docs/extensions/reference/api/tabs), [debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger), [CDP Page](https://chromedevtools.github.io/devtools-protocol/tot/Page/).

### Extension profiles and versioned ZIPs

The manager reads installed extension state on opening, then uses management events instead of polling. A profile records desired extension IDs, with always-on protection and Browser Mods excluded from disabling. Applying a profile shows its concrete changes; missing or policy-controlled extensions are reported, and failures do not erase the saved profile. Retain the actual pre-apply device state for explicit restore. Verify Chrome's user-gesture requirements through our UI/client/worker route. Sync profile definitions and deliberate preference edits, not unrequested activation changes on another device.

Package export is a separate operation/module reachable from the manager or a Store URL. It does not need the manager permission merely to accept a URL/local archive. Isolate the Store package resolver: endpoints, redirects, availability and version/platform selection need a real probe and useful failure behavior. Chrome management metadata is not an API for reading another installed extension's private files. Be explicit when exporting a published package rather than an exact installed/unpacked copy.

Read the downloaded manifest to obtain the actual version and a safe display name, resolving a localized manifest name when needed. Strip the CRX container or repack archive entries as appropriate without adding a wrapping folder. Test the ZIP with a standard extractor: `manifest.json`, scripts and assets at root, valid relative paths and a sanitized filename such as `extension-name-v1.2.3.zip`. Bound archive bytes/entries and reject unsafe paths or malformed containers. Never install or execute the package to export it. Do not add a source viewer just because the reference project has one.

Sources: [management and gesture requirements](https://developer.chrome.com/docs/extensions/reference/api/management), [CRX Viewer feature/reference](https://github.com/Rob--W/crxviewer), [downloads](https://developer.chrome.com/docs/extensions/reference/api/downloads).

### One usable video file

Start with a source-discovery and output feasibility slice before building a downloader UI. A direct file may already be the desired artifact. HLS/DASH may need segment fetching, separate audio/video track selection, timestamp handling and remuxing into one container. Preserve the original quality by preferring remuxing over re-encoding; do not force MP4 when a suitable source/container combination can avoid costly transcoding.

Use scoped, user-started discovery in the selected tab. Attach any required network observation only for an active inspection/download workflow and the relevant tab/origins. Detach it on stop, permission loss, navigation or module disable. Do not inject global fetch/player hooks or monitor all tabs by default. Load media parsing/muxing only for the job, with bounded concurrency, cancellation, storage and memory. Persist only recoverable job state locally; do not sync media URLs, cookies, signed URLs or segments.

Test direct MP4/WebM and representative non-DRM HLS/DASH, including separate audio, fragmented media, failures and cancellation. Acceptance is one file that opens in an ordinary local player, has expected duration/quality and sound, seeks, and stays synchronized. A successful HTTP download or a file named `.mp4` does not establish those properties. Live/opaque blob-player recording is a separate explicit capture workflow if real source cases require it; do not silently claim it is covered by segment downloading. DRM circumvention is outside this implementation. The user should not need to understand stream/container details to save a supported video.

Source scope: [FetchV's advertised formats and boundaries](https://chromewebstore.google.com/detail/fetchv-video-downloader-f/nfmmmhanepmpifddlkkmihkalkoekpfd).

### Per-tab mono

Prefer an explicit tab-audio processing session for the user's per-tab requirement, subject to a prototype. Capture is user-initiated; route captured audio back to playback with a tested mono downmix, and restore normal playback on stop/failure. Test left-only/right-only samples, clipping, volume/mute, navigation and tab closure. Do not build a graph or observer on every media page before the feature is used.

Chrome tab capture suppresses the tab's normal local playback, so rerouting and cleanup are essential. A worker-created stream ID can be consumed by an offscreen document on Chrome 116+, within the existing minimum-version range. Audio session ownership must coordinate with clipboard and any future recording; one feature must not stop another feature's tracks or close its document. Do not automatically restart capture on another device from synced preferences.

Sources: [toMono workflow](https://github.com/mihaimpop/toMono), [tab capture and audio playback](https://developer.chrome.com/docs/extensions/reference/api/tabCapture).

### IDN awareness, selection highlighting and refresh

Domain warnings operate on normalized hostname labels, including TLDs/subdomains, not text search over the whole URL. Use a maintained standards-based decoder for display; preserve ASCII/Punycode alongside Unicode. IDN is not itself evidence of phishing. Match allowlists exactly with explicit subdomain semantics. If the selected behavior requires a warning before the destination loads, prototype declarative main-frame interception and its permission/redirect rules. A notification after navigation must not be described as preventing page execution. No remote reputation calls or per-page DOM scan is needed for hostname detection.

Highlight using the CSS Custom Highlight API where supported, preserving DOM structure and current selection. Build/search a bounded text-node index only while enabled; coalesce selection changes, skip editable/password fields and clear owned ranges/listeners on disable/navigation. Scope any mutation observer to this active feature; do not rescan an entire large document for every selection or mutation. First acceptance covers selected-text matches, dynamic pages, large documents, frame access and teardown, without persistent annotations.

Refresh schedules are local device jobs, with persisted intent/deadline and alarm reconciliation after worker restart. Skip missed refresh bursts after sleep; cancel owned alarms on stop/close/disable. Define same-tab navigation behavior explicitly before implementation. Chrome 127 remains the supported floor: its lifecycle documentation describes the 30-second alarm minimum introduced in Chrome 120, while current API docs describe a lower limit. Verify the supported-version behavior before offering short intervals or relying on newer persistence fields. Do not keep a worker/offscreen page alive just to manufacture precise timers.

Sources: [Unicode Domain Warning](https://chromewebstore.google.com/detail/unicode-domain-warning/khijgpndoffkmanglickjbnkbjimcdhn), [declarative rules](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest), [selection reference](https://github.com/neaucode/selection-highlighter), [CSS Highlight specification](https://www.w3.org/TR/css-highlight-api-1/), [alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms), [version-specific lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

## Shared architecture work before integration

Keep the existing feature/domain/adapter/UI boundaries; create the proposed module folders only when implementing them. Composition routes cross-feature commands through explicit public contracts. This list is not a reason to create a generic plugin framework or shared mutable feature registry.

1. **Redact page shell:** implement the first real options/palette slice with the verified esbuild aliases. Extend TypeScript/JSX, typed lint, dependency/context checks, Knip and negative fixtures to cover TSX. Assert that native React and unrelated feature bundles do not enter the UI/worker outputs. Use the shared theme and test each adopted control/adapter.
2. **Module lifecycle and permissions:** centralize enable/disable and permission-change handling. Feature factories own listeners, observers, timers and jobs. Disabled modules do no feature-specific work; shared control-plane events remain bounded. Request optional capabilities for their actual workflow and verify which permissions can be optional.
3. **Shared offscreen ownership:** clipboard currently creates the document in its own adapter. Before audio/composition consumers, introduce a narrow platform/composition service with serialized creation, explicit job/session leases, legitimate creation reasons, restart reconciliation and safe release. Chrome permits one offscreen document per profile context, not one per feature. Its extension API calls go through runtime messaging. Test simultaneous clipboard/mono use, failed/concurrent creation, reason/capability changes and worker reconnection; releasing a copy/PDF job must not interrupt active audio.
4. **Jobs and status:** capture/download/refresh jobs need bounded progress, cancellation, error recovery and coordinated badge/status ownership. Store feature-owned data behind ports; share lifecycle primitives only when a second real caller needs them. CPU-heavy archive/PDF/media work must not run in the service worker or block ordinary UI interaction.
5. **Settings and shortcuts:** validate versioned feature settings at boundaries, preserve deliberate user intent/conflict resolution and keep content/jobs local. Register new actions in the typed catalog without changing old IDs or consuming extra suggested-default slots. File bytes, selections and media URLs are not preference-sync data.

Sources: [offscreen limits](https://developer.chrome.com/docs/extensions/reference/api/offscreen), [optional permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions). Existing [architecture](architecture.md), [dependency decisions](dependencies.md) and [feature admission](feature-admission.md) remain applicable. Store scope still needs review before publication; this plan does not change the one-extension direction or promise Store acceptance.

## Proposed implementation order

1. Prove the consequential paths early with disposable fixtures: full-image clipboard/large PDF, versioned root ZIP export, single-file HLS/DASH with audio, and mono playback/restoration. Resolve capture privileges, supported formats and peak-memory limits before a broad UI build.
2. Build the Redact shell, lifecycle/permission services and extension manager **including profiles/bulk toggling** as the first substantial UI slice. Make package export reachable from it without coupling the two modules' internals.
3. Deliver screenshot/clipboard/PDF and simple refresh; add per-tab mono after shared offscreen ownership is verified. Build selection and domain warnings as separately enabled modules with idle/teardown checks.
4. Deliver supported single-file video saving behind its own job UI and lazy processing path. Keep format support tied to verified playback fixtures, not a universal downloader claim.
5. Reconcile priorities with the existing Quick Bookmark, shortcut, tab-discarding, middle-click search, Omnivore and media-control migration work; do not delete those commitments or disable old extensions prematurely.

This order is a proposal, not a delivery-date estimate or approval of every optional upstream feature. Each implementation gets a focused decision with actual permissions, lifecycle, failure cases, migration and measurements. Compare popup/worker cost with modules disabled as well as active workloads; page-count multiplication, idle wakeups and cleanup matter more than dependency bytes alone.
